## Requirements and distinguishing cases

- I1 Feedback: after success, changing a draft clears Saved; a subsequent rejected write shows Save failed and never Saved. Blank validation also cannot leave stale success. Existing/new failures retain exact draft including whitespace/completion, prior rows and exact stored bytes. Retry saves trimmed title/completion and survives reload.
- I2 Stale snapshots: two same-origin tabs edit the same record or different records. After A commits, stale B must not write its whole snapshot. Show conflict, preserve B draft and exact A bytes. Ordinary Save cannot silently accept stale state.
- I3 Recovery: load latest preserves the draft, displays latest rows, performs no write, and leaves ordinary Save blocked. Explicit Save draft as new appends against latest data under the same serialization, allocates a fresh safe integer ID and preserves both contributions. Cancel after conflict reloads latest and closes editor; user can then deliberately reopen/edit. No automatic overwrite/rebase/merge.
- I4 Overlap: deliberately overlap cooperating saves (A held inside lock before read/commit, B requested while held). A commits; B must detect stale bytes after obtaining lock. Repeat existing and new-record collision scenarios and reverse winner order. Recovery copies allocate against latest so two overlapping copies cannot reuse an ID.
- I5 Capability/failure: missing/refused lock or storage read/write failure never falls back to an unlocked write. No ID beyond Number.MAX_SAFE_INTEGER; failure preserves draft/store. Recovery cannot replace malformed latest data. A normal unchanged malformed-startup store retains historical seed-and-explicit-save repair; actual unreadable startup must not be treated as a known empty store.
- U1 Unaffected workflows: seed/empty/sparse stores, new/edit/save/cancel, trim/Unicode/markup text, validation, done flag, filter/selection, Enter submission, saved reload/fresh tab, unsaved reload loss, malformed schema recovery. Compare original/parity to source-informed expectations and improved results with declared feedback differences.

Original/parity must visibly fail selected I1/I2/new-ID collision improvement expectations, while their historical outputs remain expected baseline observations. Improved results evaluated separately; no parity claim for deliberate changes.

## Design decision and boundaries

Proposed: exclusive Web Lock pocket-board-v1:write, compare full raw baseline bytes inside lock before ordinary write; allocate new IDs and save-as-new against latest under that lock. Exact bytes intentionally cause conservative conflicts even for unrelated edits. No revision/event check is described as serialization. W3C Web Locks draft https://www.w3.org/TR/web-locks/ explains cooperative storage-bucket lock scope; runtime capability still to be observed. No working capability means writes fail closed. No lock stealing/timeouts. Waiting state disables app edits; fixture release is outside app. Drafts remain in memory; no reload-proof draft storage is promised.

Lock cooperation is required across writers sharing the browser storage bucket. Original/external writers ignore this lock and can race; same-byte ABA changes are undetected; storage-engine durability, malicious writers and multi-device coordination are excluded. Save success means synchronous storage API acceptance, not power-loss durability. Controlled rejection/lock hold/missing-capability wrappers are labeled fixture instrumentation, not real browser denial. Actual process restart, real quota/permission denial, engine/profile identity and cross-browser/model/host properties remain unrun/unknown unless new supported evidence resolves them.

Use supported IAB UI actions, read-only DOM/storage evaluation and explicit fixture setup/reset UI. Separate loopback ports isolate reference/parity/improved; deliberately shared tabs use one target origin. Allowlisted local server only, owned tabs only, historical originals preserved. Retain failed actions, complete unique checkpoints and independent expected assertions. Package teaching example and bounded observed report; no general reliability certification. Freeze amendments explicitly if evidence forces a consequential change.

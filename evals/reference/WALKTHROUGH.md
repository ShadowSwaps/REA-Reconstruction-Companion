# Worked investigation: from observations to a compatibility decision

This example shows how the companion turns evidence into a scoped contract before implementation. It uses actual local REA analysis and recorded runs of Pocket Tasks 1.0.0. The maintainer had already seen the source and reviewer tests, so this is a **maintainer-informed investigation example**, not an independent reconstruction, a blind evaluation, or a certification of any AI host. There is no candidate implementation or candidate score here.

The example is reviewer/training material. Reading it exposes answers. Keep it outside a candidate's permitted evidence during a fresh trial, and disclose prior exposure. The packet preparer still exports only `TASK.md`, the target, and its identity.

## Scope and identity

- Subject: selected state, editing, and persistence workflows in a small command-line app.
- Carrier: the supplied JavaScript artifact. Objective: understand and specify original behavior, including quirks; no implementation or behavior change in this example.
- Target SHA-256: `8ad2586a3adb43e19c55ead2999346ccbd416d0559226046aa0738bab188afb7` (6,417 bytes).
- Source package: companion v1.3.1, commit `04bcb50b12ba7c1dc272c0c778c98e6d3793bc9f`. The artifact remains Pocket Tasks 1.0.0; these versions describe different things.
- Only disposable task stores and existing local tools were used. No package installation, extra model worker, paid service, or remote target was used for the investigation.

The brief asks: What survives a restart? What does cancel restore? Does selection follow a task or a row? Can a failed save destroy existing data? These questions select the probes below. They do not establish full app parity.

## What REA established, and what it did not

The existing REA connection received `analyze_javascript_application` for the packet's `target` directory, with `format: directory`, `detail: summary`, a 30,000 ms analysis timeout, 256 MiB old-space budget, and 5,000 semantic nodes per file/application. The source was parsed as inert text; this call did not execute it.

[rea-excerpt.json](walkthrough/rea-excerpt.json) retains selected returned fields, actual Evidence IDs, parameters, identity, coverage and limitations. It is explicitly a sanitized derivative, **not a canonical Evidence bundle or a signature**. Private paths and the full graph are omitted. Evidence IDs identify the original records, not the edited excerpt; reruns may have different IDs. The recorded provider version `1` identifies the analyzer, not the REA package distribution. A distribution version was not captured.

REA reported one parsed JavaScript file, 6,417 text bytes, 1,120 visited AST nodes and no parse failures. Its asset view matched the SHA-256 above. Application coverage was `complete`, but semantic coverage was `unknown`, with **230 semantic unknowns**. Those are different scopes: successful parsing is not complete behavioral understanding. The summary's `modules: 0` field also does not mean no source was examined; the module page returned six graph entries at the same path, and the asset entry supplied its byte identity.

This was enough to identify the artifact and preserve analysis limits. It did not prove save behavior, selection semantics, performance, or runtime reachability. Ordinary inspection of `session`, `visible`, `selected`, and `snapshot` in [the source](target/pocket-tasks.mjs) suggested a row-index mechanism. That source reading is recorded separately from REA's returned facts. The runtime experiments test its observable consequences.

## Recorded experiments

[runtime-observations.json](walkthrough/runtime-observations.json) contains seven scenarios and ten process sessions. Each scenario was run twice from a fresh directory; both captures matched. Each record retains exact UTF-8 stdin, stdout, stderr, exit status, and store/pending-file contents. `null` means a file was absent. Sessions within one scenario share a store; different scenarios start independently. Responses were captured from the reference, not generated by an implementation under evaluation.

| Evidence | Question and observation | Limit |
| --- | --- | --- |
| W1 | Adding `  Café 😀  ` makes the draft dirty and preserves whitespace/Unicode. No file appears. Restart returns the seed without the added item. | One unsaved-edit sequence, not every input boundary. |
| W2 | Saving Delta persists it. Toggling Gamma under the `done` filter hides it; cancel restores it and keeps that filter/row selection. Restart retains Delta but resets filter to `all` and selection to null. | Normal single-writer save/restart, not crash durability. |
| W3 | Selecting row 0 selects Alpha. Filtering to `done` selects Gamma without another select. Rename changes Gamma. Cancel restores Gamma's title; filtering back selects Alpha. | One contrast that distinguishes row selection from stable task selection. |
| W4 | Selecting Beta and removing it moves selection to Gamma. Cancel restores Beta and selects it again. | This removal position, not every selection boundary. |
| W5 | A valid empty store stays empty after save/restart. Invalid selection fails. Blank rename reports `invalid-title`; a valid title without selection reports `no-selection`. | Tested error precedence only. |
| W6 | Malformed existing JSON causes exit 2, no stdout, and unchanged stored bytes even when the input requests save. | One malformed input; not a full parser corpus. |
| W7 | A pre-existing `.pending` file makes save report `save-failed`. Both existing files remain byte-identical; the draft remains dirty. | Collision handling, not hostile filesystem races or concurrent writers. |

For example, W3 sends this array in one process with a missing disposable store:

```json
[
  { "op": "select", "index": 0 },
  { "op": "filter", "value": "done" },
  { "op": "rename", "title": "Renamed" },
  { "op": "cancel" },
  { "op": "filter", "value": "all" }
]
```

The successive `view.selected` values are `t1`, `t3`, `t3`, `t3`, `t1`. Dirty state is false, false, true, false, false. The full response objects remain in W3; this table is only a reading aid.

**Inference:** a retained visible-row index explains both W3 and W4 and agrees with the inspected source. The runtime traces directly establish those sequences, not every possible transition. Static and dynamic evidence concern the same authored target and investigator; they are corroborating views, not independent evaluators.

## Requirements and acceptance checks

These are compatibility requirements for the observed slices. Each keeps its evidence and a proposed reconstruction check together. The reference's internal implementation is not automatically the required implementation architecture.

| Requirement | Required behavior and rationale | Evidence → acceptance check |
| --- | --- | --- |
| R1 Draft isolation | Unsaved edits affect the current view only; preserve accepted title bytes. | W1 → replay both sessions against a reviewed candidate and compare outputs and file absence. |
| R2 Save/restart | Explicit save persists task content/IDs; a new process resets transient selection/filter state. | W2 → compare the saved schema-1 data and restarted view. |
| R3 Cancel | Cancel restores saved task data, keeping current filter and selected row index. | W2–W4 → compare content, visible selection and dirty state after cancel. |
| R4 Selection compatibility | Preserve the observed retargeting through filter/removal for this parity task. Do not silently substitute selection by stable ID. | W3–W4 → assert the selected ID and affected title after each step. |
| R5 Empty/error state | Preserve a valid empty store, reject tested invalid commands, and preserve malformed input bytes on startup failure. | W5–W6 → compare command errors, empty restart, exit status and unchanged file. Diagnostic wording is not a candidate compatibility requirement. |
| R6 Save failure | On the tested pending-file collision, report failure, retain a dirty draft and preserve both foreign files. | W7 → assert `save-failed`, dirty state and byte-identical files. |

The recorded expectations must remain separate from future candidate output. The walkthrough replay checks exact original bytes, including diagnostics, to detect documentation drift. A candidate review uses the scoped contract and the [reviewer checker](README.md#3-review-code-then-compare-behavior), whose compatibility boundary does not require identical diagnostic wording. Do not rewrite captured outputs just to make a candidate pass.

## Quirk decision: document it, flag it, then choose deliberately

**Observed:** W3's selected task changes after filtering. **Consequence:** a user can rename or toggle a different task than the one they originally selected. W4 shows a related surprise after removal. **Compatibility decision:** retain this behavior in the reference parity task, because that task explicitly requests original behavior.

**Proposed improvement, not implemented:** store a stable selected task ID; clear selection when that task is hidden or removed. If approved for a new product, add separate tests: filtering Alpha out yields no selection, and deleting Beta cannot silently select Gamma. Retain the original traces as the record of deliberate divergence. Approval to reconstruct an app does not by itself decide whether all its quirks should be copied; use the user's compatibility goal.

## Proposed implementation boundary and checkpoint

A portable reconstruction could use an input validator, a session state reducer, a store adapter, and a JSON process adapter. Keep saved and draft data separate; model transient filter/selection explicitly. These are **design proposals**, not a claim that REA recovered four original modules. Any already available language may implement the interface without additional charges.

Start with view/edit/cancel, then add save/restart and failure handling. Use R1–R6 as slice checks. Before implementation, a reviewer should confirm the compatibility decision and which remaining boundaries matter. This example stops at that checkpoint; it neither asks a new model to run nor executes an unreviewed candidate.

Still unresolved here: full input/capacity boundaries, all command sequences, hostile path races, crash durability, concurrency, UI behavior and production performance. Existing regression tests cover some more cases, but their existence does not turn these ten observations into a complete investigation. No performance improvement is claimed without measurements.

## Repeat the observations

From a trusted checkout or extracted package, with existing Node.js 20+:

```sh
node --test tests/reference-walkthrough.test.mjs
```

The test runs only the repository-owned target in fresh temporary directories. It first checks the target's hash against the captured identity, then compares the recorded process and disk results. It uses no packages, network, models, REA calls or candidate command configuration. Temporary stores are removed afterward. A passing replay establishes that these observations still match the artifact on the tested runtime; it does not reproduce the historical REA session or verify the prose, instruction following, skill discovery, automatic integration, independent reconstruction, or human approval.

To perform a new investigation, use the [full procedure](README.md), create a fresh packet, and verify it before and after. Run REA through your existing supported tool interface against that packet and preserve the returned coverage/unknowns. Use ordinary process execution for the recorded probes; REA static analysis and shell runtime observations are distinct evidence sources. Do not install an engine or start a metered model run just to reproduce this example.

The packet was prepared from v1.3.1; REA's asset hash matched that prepared identity. It passed the read-only verifier after the investigation. A separate pre-investigation `--verify` invocation was not recorded, so this example does not claim completion of every procedural step. The final check establishes integrity at check time, not a signature or permission to publish.
